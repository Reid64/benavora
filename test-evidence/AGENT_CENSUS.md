# AGENT_CENSUS.md — Full Agent Census (AR-13.1)

**Date:** 2026-09-19
**Scope:** Every agent module in `scripts/audit/agent-exercise-registry.ts` (144 modules, verified below), one row per module, built entirely from live production data (Supabase project `vbjplpquqxxfbpazyalt`) and direct source-code invoker tracing — never from AGENTS_v2.md, AGENT_INVOCATION_MAP.md, or any prior narrative doc, except where those docs are cited as prior evidence to build on.

This document changes no production code. It is the ground-truth input for every later phase's agent-repair prioritization.

## Method

1. Read `scripts/audit/agent-exercise-registry.ts` for the authoritative module list (144 entries — confirmed by direct count below).
2. Queried `agent_runs`, `pil_agent_runs`, `pil_agent_registry`, and `ai_usage_log` live via the Supabase SQL execution tool against project `vbjplpquqxxfbpazyalt` for real counts, statuses, timestamps, and item-processed medians. No estimates.
3. Fanned out 4 parallel research agents (further split into 5 sub-batches for the largest family) to trace the real INVOKER for every module — grepping `worker/**`, `src/app/api/**`, and cron/scheduler tables for actual call sites with file:line citations — and to score the deterministic/agentic rubric from the actual source code, not the registry's claims about it.
4. Cross-checked every finding against the task's anchor facts and `test-evidence/AGENT_INVOCATION_MAP.md`; disagreements are reported explicitly below, not silently resolved in either document's favor.

## Anchor-fact reconciliation

- **"144 agent modules on disk"** — CONFIRMED EXACTLY. `BASE_AGENT_SPECS` (54) + `AUTONOMOUS_AGENT_SPECS` (27) + `PIL_AGENT_SPECS` (51) + `AUTOAPPLY_AGENTS` (9) + `PLAIN_FUNCTION_AGENTS` (3) = 144.
- **"93 agent types have executed (69 core, 24 PIL)"** — PARTIAL MISMATCH, reported not overridden. Live query found exactly 69 distinct `agent_type` values in `agent_runs` and 24 distinct `agent_id` values in `pil_agent_runs` (24 matches exactly). But only ~52-55 of those 69 core-table types map onto a distinct registry module (the registry documents two intentional `agent_type` collisions: `browser_automation` and `corporate_research`, each shared by two modules). The remaining ~14-17 distinct `agent_type` values are either non-registry orchestrator/wrapper rows (`autoapply_queue_processor`, `autonomous_orchestrator`) or real agent classes that were simply never added to the 144-module registry (`narrative_drafting`, `ag22_propensity_scoring`/AG-22 PropensityScoringAgent, `fit_analysis`, `ag-26-forecast`, `ag-43-funder-signals` — see **Registry-gap agents** below). The registry, while accurate for what it lists, is itself incomplete relative to live production history.
- **`ag-29-knowledge-indexer` headline** — CONFIRMED AND ROOT-CAUSED. 64,481 lifetime runs (up from 63,941 three hours before this session per the task's own anchor, consistent with continuous ~10s firing), 64,480 completed, 64,477 (99.995%) with `items_processed=0`, ~96% of every row in `agent_runs`. **Root cause, established by direct live query this session:** `foundation_directory` has 133,812/133,812 rows with `embedding IS NULL`, and every one of those 133,812 rows has `programs=NULL` and no `enrichment.mission` key — the only two text sources the agent's own `flattenFoundationText()` can index. The WHERE-embedding-IS-NULL query and content-filtering logic are **correct, not buggy**; they accurately detect zero indexable text on every single pass. This is a permanent, structural gap in `foundation_directory`'s own ingestion pipeline (it never populates `programs` or `enrichment.mission` for any row — the agent's own file header already flags this), not a broken agent and not a benign backlog that will clear itself.
- **`autoapply_queue_processor` "0 completions across 37+ runs"** — CONFIRMED AND UPDATED to 0/59 by this session. Root cause: the first 55 failures were legitimate `SkipError`/business-rule rejections against synthetic test orgs, mis-logged as `failed` by a `run-logger.ts` classification bug (fixed this cycle — migration 199 adds a `skipped` enum value, which explains the 3 `other_status` rows that appeared afterward); the remaining recent failures trace to a separately-found, still-referenced `FormAnalyzerAgent` bug (never calls `page.goto()` on first encounter with a funder, caching a poisoned 0-field template for 7 days). Zero confirmed organic completed submissions exist in this codebase's history.
- **"orchestration_logs capturing but 100% ag-29 heartbeat in last 3 hours"** — not independently re-verified this session (outside this task's live-query scope), but fully consistent with the finding above.

## Registry corrections found (source code disagrees with the registry)

1. `src/lib/agents/ea-04-foundation-detector.ts` — registry says `callsClaude:true`; the file has zero `callClaude` import and its own header states "purely deterministic." Registry is wrong.
2. Five `AUTONOMOUS_AGENT_SPECS` entries omit `callsClaude` (defaults `false`) but genuinely call Claude at runtime, confirmed via real call sites: `ag-30-donor-intent`, `ag-35-community-need`, `ag-09-outcome-analyzer`, `ag-11-knowledge-gap`, `ag-32-relationship-graph`.
3. `pilAgentDescriptor()` hardcodes `callsClaude:true` for all 51 PIL codes, but roughly 25 of the 51 modules (all of REL-02/04/05/06, all of QLF, all of KNW, all of STR, OPS-01, all of APP) make **zero** Claude or PIL-tool calls in their actual source. The DIS and INT families (and a handful of REL/SUP) do genuinely call Claude tools; most SUP/QLF/KNW/STR/OPS/APP agents are pure deterministic logic over prior evidence rows despite the blanket registry flag.
4. `BEN-STR-01/02/03` were omitted from the task brief's own framing (~24 PIL never-invoked), but a direct live query confirms these three also have zero lifetime `pil_agent_runs` rows. **The true PIL never-invoked-or-orphaned count is 27, not 24.**

## Three most surprising findings

1. **`ag-29-knowledge-indexer`'s 96%-of-all-`agent_runs` no-op is not a bug — it's the correct, efficient behavior of a query hitting a permanently empty well.** Every one of the 133,812 rows it's supposed to embed has zero indexable text because `foundation_directory`'s own ingestion pipeline never populates the two fields (`programs`, `enrichment.mission`) the indexer reads. Fixing the indexer changes nothing; the fix belongs in `foundation-scraper.ts`.
2. **`src/lib/agents/form-filler.ts` has no approval gate at all** — it fills and clicks submit on a live funder form directly inside `execute()`, with zero human review, apparently contradicting the "Automation NEVER auto-submits forms" contract that `playwright-agent.ts` visibly enforces two files away. It has 0 lifetime production runs, so this is a dormant risk, not an active incident — but it is real, live code.
3. **The PIL pipeline has never once organically completed all 9 families for a single research run.** `BEN-SUP-05` (the critic agent every submission path depends on) is 100% unreachable due to a dropped `plan.targetAgentRunId` field in `AgentRunner.delegate()`; `BEN-APP-03` (the final AutoApply-handoff step) has 0 lifetime runs; and 24-27 of 51 PIL agents have never fired despite `pil_agent_registry.active=true` for all 51. No prospect has ever been carried by PIL research all the way to an AutoApply submission.

Six `agent_type` values have real, executed production history in `agent_runs` but no corresponding module in the 144-item registry — a gap in the registry itself, not in this census. See the **Registry-gap agents** table at the end of this document for full detail.
