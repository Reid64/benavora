# MIGRATION_IDEMPOTENCY_AUDIT.md

Generated by `scripts/check-migration-idempotency.ts` (`pnpm check:migrations`). Real static analysis of every migration file's top-level SQL statements in both migration directories, plus a best-effort live re-run spot-check against production wrapped in `BEGIN; ... ROLLBACK;` (nothing is ever committed by this harness).

Per project history, which of the two directories below is the actual live-applied source of truth against production is disputed/unresolved — this audit deliberately does not resolve that; it covers both as they exist on disk, since either may end up being the real one. See memory `benavora-two-parallel-migrations-directories`.

Static analysis and the live spot-check below never mutate anything (spot-checks are wrapped in `BEGIN; ... ROLLBACK;`). A separate, opt-in **dry-run mode** (`pnpm check:migrations:dry-run`) actually applies every migration in `src/supabase/migrations` against a disposable database (never production) and reports the first one that fails or is destructive with no down-migration — see `MIGRATION_DRY_RUN_REPORT.md` if that mode has been run.

## Methodology notes

- Static analysis parses each file's top-level SQL statements with a real tokenizer that tracks single-quoted string literals, `--` line comments, `/* */` block comments, and `$tag$`-quoted bodies (DO blocks, function bodies) so semicolons inside them never incorrectly split a statement.
- `CREATE POLICY`/`CREATE TRIGGER`/`ADD CONSTRAINT` are considered guarded if the file contains a matching `DROP POLICY IF EXISTS` / `DROP TRIGGER IF EXISTS` / `DROP CONSTRAINT IF EXISTS` of the same name earlier in the same file (the idiom already used elsewhere in this repo, e.g. migration 128) — not just a bare `CREATE ...`.
- `CREATE TYPE ... AS ENUM` at the top level (outside a `DO $$ ... EXCEPTION WHEN duplicate_object ...` block) is always flagged non-idempotent — Postgres has no `IF NOT EXISTS` for this statement form at all.
- `ALTER TABLE ... RENAME COLUMN` is always flagged non-idempotent — Postgres has no guard mechanism for it under any syntax.
- `GRANT`/`REVOKE`/`COMMENT ON`/`ENABLE|DISABLE ROW LEVEL SECURITY`/plain `UPDATE`/`SELECT`/`SET` statements are not classified — they are either inherently safe to re-run or outside this harness's DDL-idempotency scope.
- This is heuristic regex-based static analysis of real SQL text, not a full SQL parser — it can misclassify unusual formatting it hasn't been calibrated against. Treat findings as a strong signal, not a proof.

## 2026-08-21 update — migration-drift remediation: ledger reconciled, 48 migrations applied to production

Confirmed live (independently of this file's own static analysis): `supabase_migrations.schema_migrations` did not exist in production at all before today — this project has never run `supabase db push`. A new ledger-vs-reality audit (`test-evidence/remediation/migration-drift/ledger-audit.md`, a new script, `scripts/audit-migration-ledger.ts`, that probes production for every object each root `supabase/migrations/` file creates or alters) found, of 145 files: 90 APPLIED-UNRECORDED, 28 PARTIAL, 19 MISSING, 8 NO-OP.

Rehearsed all 47 PARTIAL+MISSING files against a disposable Postgres 17 (matching production's real version — not 15) container, in filename order, one transaction each. First pass found 9 real failures — of which most were exactly the class of non-idempotent statement this file already documents (unguarded `CREATE TYPE ... AS ENUM`, `CREATE TABLE`, `CREATE POLICY`, `CREATE INDEX` — see `002_phases_2_5.sql`, `037_giving_history.sql`, `038_intelligence_tables.sql`, `041_scraping_targets.sql`, `054_email_calendar_integration.sql`, now all fixed with the same `IF NOT EXISTS`/`DROP POLICY IF EXISTS`/`DO $$ ... EXCEPTION WHEN duplicate_object` idioms this file's own methodology already checks for). Three files (`050_funder_credentials.sql`, `052_webhook_configs.sql`, `095_discovery_matches.sql`, `096_knowledge_engine.sql`) had a different, more serious class of bug this static-analysis harness cannot see: real column/table-name drift between the checked-in migration file and a table that already existed live with a different shape (created out-of-band) — `organization_members` referenced by policies but never existing anywhere in this schema; `webhook_type`/`active` instead of `type`/`is_active`; `org_id` instead of `organization_id`. All fixed and verified against real production data before applying (each affected table confirmed empty first, or the real live policy text pulled via `pg_policies` and matched exactly).

47/47 applied clean to production after fixes (three consecutive clean rehearsal passes from a fresh prod dump first). One further gap surfaced only after production apply, by `src/__tests__/integration/rls.test.ts`'s full cross-org sweep (not by this file's own idempotency-only methodology, and not something the ledger-audit script's object-existence probe could see either): `052_governance_layer.sql` and `053_multichannel_analytics.sql` create 4 org-scoped tables (`ab_test_variants`, `funder_relationships`, `session_recordings`, `submission_usage`) but never enabled RLS on any of them at all — a real, live cross-org leak for the short window between apply and fix. Closed via a new `144_governance_analytics_rls_hardening.sql`. A second post-hoc gap, found by manually re-verifying WGR-042/WGR-043 against live columns rather than trusting the ledger-audit script's table-existence-only check: `funder_giving_history` and `success_probability_scores` both already existed live with a different column set than their migration files define (the same table/policy drift class as 050/052/095/096 above, just not one this session's rehearsal happened to exercise since neither table's *own* creation failed — only some of the columns inside it were silently never added). Closed via a new `145_giving_history_and_probability_scores_column_drift.sql`.

Also hardened `003_onboarding.sql`'s unguarded backfill (`UPDATE organizations SET onboarding_completed = true` with no `WHERE` clause — flagged P1 by a prior idempotency dry-run for silently re-corrupting any org that has legitimately diverged since the first run) with a `WHERE onboarding_completed IS NOT true` guard.

**Known methodology gap in `scripts/audit-migration-ledger.ts`** (the new ledger-vs-reality script, not this file's own harness): it only verifies a `CREATE TABLE`'s *target table* exists, not that an already-existing table's column set matches the file's inline column definitions — `ALTER TABLE ... ADD COLUMN` statements are checked per-column, but columns defined inline inside `CREATE TABLE` are not, once the table already exists. This is exactly how `037_giving_history.sql`/`038_intelligence_tables.sql`'s real column drift (WGR-042/WGR-043) went undetected by the first rehearsal pass and had to be caught by manually re-verifying the register's own claims against live columns after the fact, not by the automated tooling. Documented here so a future session extends the script rather than re-discovering this gap.
