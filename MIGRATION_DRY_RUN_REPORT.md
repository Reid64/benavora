## Methodology notes

- Scope is deliberately `src/supabase/migrations` only, not both migration directories — a migration here that depends on a table/type created only in the root `supabase/migrations/` tree will legitimately fail to apply against a bare disposable database. That is real signal about this tree's self-containedness, not a harness defect — see the note at the top of this script's "Dry run" section.
- "Applied cleanly" commits each file for real (not wrapped in a throwaway transaction) so later files see earlier files' actual schema changes, matching how these migrations would really be replayed in order.
- The idempotency re-apply immediately follows each successful apply, wrapped in `BEGIN; ... ROLLBACK;` so the re-apply attempt never actually double-commits.
- Destructive-statement detection (DROP TABLE/TYPE, ALTER TABLE DROP COLUMN, TRUNCATE, DELETE with no WHERE) is a static text scan of every file's top-level statements, run independent of whether that file was actually applied this pass — so it still covers files skipped after an earlier failure.
- No down-migration convention exists anywhere in this repo as of when this harness was written — expect every destructive statement found to report "NO" down-migration until one is adopted.
- This run's disposable database is never torn down by this script — see `DRY_RUN_SETUP_INSTRUCTIONS` (printed when `DRY_RUN_DATABASE_URL` is unset) for the matching teardown command for whichever setup path was used.
