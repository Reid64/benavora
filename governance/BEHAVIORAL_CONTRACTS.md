## API Contracts
#### Conventions
- All API routes are implemented as Next.js 14 App Router Route Handlers under /app/api/
- organization_id is ALWAYS derived from the Supabase Auth session (supabase.auth.getUser()) — never accepted from request body or query params
- All Supabase queries are executed with the service-role client only after session verification; RLS policies enforce organization_id scoping on every multi-tenant table
- Request body parsing uses zod schemas; validation errors return HTTP 400 with code VALIDATION_ERROR and a field-level errors array
- Successful responses use envelope { data: T }; errors use { error: { code: string, message: string, fields?: Record<string,string> } }
- All timestamps are ISO 8601 UTC strings in API responses
- Monetary amounts are stored and transmitted as integers in cents; API responses include a formatted display string alongside the raw integer
- Pagination uses { page: number (1-indexed), limit: number (default 25, max 100) } query params; responses include total count
- PATCH routes accept partial payloads; omitted fields are not modified (no implicit nulling)
- All POST mutation routes that modify AI-scored fields log the model name, prompt version, and raw response to an audit_logs table
- Supabase Realtime subscriptions are used on research_run_agents and alerts tables for live UI updates; no polling fallback needed
- The /api/research/run endpoint spawns agent tasks using Promise.allSettled and persists results transactionally; it responds immediately with the run ID while processing continues asynchronously
- Route /outcomes performs a Next.js permanent redirect (HTTP 301) to /analytics at the framework routing layer, not as an API route
- All Recharts components on the /analytics page are loaded with dynamic(() => import(...), { ssr: false }) to prevent SSR hydration mismatches
- Agent timeout is enforced via Promise.race with a 90-second AbortController signal per agent task
- AI provider retries: single retry after 5-second delay on HTTP 429; no retry on other errors
- Eligibility scoring is triggered asynchronously after grant INSERT via a queued background task; it does not block the research run response
- Stale running research runs (started_at older than 10 minutes) are marked failed by a Vercel Cron job at /api/cron/cleanup-stale-runs scheduled every 10 minutes
- TypeScript strict mode is enabled; all route handler request/response types are explicitly typed with no implicit any

#### Flows
- **Sign Up**
  1. User navigates to /signup
  1. User submits email, password, organization name, and full name
  1. Frontend calls supabase.auth.signUp({ email, password, options: { data: { full_name, organization_name } } })
  1. Supabase Auth creates auth.users row and sends confirmation email
  1. Supabase DB trigger on auth.users INSERT fires create_organization_and_user() function
  1. Trigger INSERTs new row into organizations table with name=organization_name, plan='free'
  1. Trigger INSERTs new row into users table with id=auth.uid(), organization_id=new_org.id, role='admin'
  1. User clicks confirmation link in email; Supabase sets email_confirmed_at
  1. User redirected to /dashboard on successful session establishment
  1. If confirmation pending: user sees /signup/confirm-email holding page
- **Log In**
  1. User navigates to /login
  1. User submits email and password
  1. Frontend calls supabase.auth.signInWithPassword({ email, password })
  1. On success: Supabase returns session with JWT containing user id and role claim
  1. Frontend stores session via Supabase Auth cookie helper (createClientComponentClient)
  1. Middleware reads session cookie, fetches user row from users table to confirm organization_id and role
  1. If user row missing or fetch fails: middleware redirects to /login immediately (Iron Law 4)
  1. If user row valid: middleware sets request headers x-user-id, x-organization-id, x-user-role
  1. User redirected to /dashboard
  1. On invalid credentials: toast error 'Invalid email or password. Please try again.'
- **Log Out**
  1. User clicks 'Sign Out' in sidebar or settings menu
  1. Frontend calls supabase.auth.signOut()
  1. Supabase clears session cookie
  1. Middleware on next request finds no session, redirects to /login
  1. User lands on /login page

  1. Frontend calls supabase.auth.resetPasswordForEmail(email, { redirectTo: '/reset-password' })

- **Session Refresh and Protected Route Access**
  1. User navigates to any protected route (not /login, /signup, /forgot-password, /reset-password)
  1. Next.js middleware intercepts the request
  1. Middleware calls createMiddlewareClient(req, res).auth.getSession()
  1. If no session found: middleware returns NextResponse.redirect('/login') immediately
  1. If session found but expired: Supabase client auto-refreshes token using refresh_token cookie
  1. If refresh fails: middleware returns NextResponse.redirect('/login') immediately
  1. If session valid: middleware queries users table for user row matching auth.uid()
  1. If users query returns error or empty: middleware returns NextResponse.redirect('/login') immediately — never renders page
  1. If users row found: middleware attaches x-user-id, x-organization-id, x-user-role to request headers
  1. Request proceeds to Next.js App Router page or API route handler
- **Role-Based Access Control Enforcement**
  1. API route handler reads x-user-role and x-organization-id from request headers set by middleware
  1. Handler checks role against required permission for the operation
  1. If role insufficient (e.g., member attempting admin-only action): return HTTP 403 with { error: 'Forbidden' }
  1. Supabase RLS policies independently enforce organization_id scoping on all DB queries
  1. If RLS policy rejects query: Supabase returns empty result or error; API returns HTTP 403
  1. Frontend receives 403: displays toast 'You do not have permission to perform this action.'
  1. No sensitive data from other organizations is ever returned due to dual enforcement (middleware headers + RLS)

#### Middleware
The Next.js 14 App Router middleware is defined in /middleware.ts at the project root. It runs on all routes matched by the config matcher, which excludes: /_next/static, /_next/image, /favicon.ico, /api/auth (Supabase Auth webhook callbacks), /login, /signup, /forgot-password, /reset-password, and /accept-invite. For all other routes (all protected pages and API routes), the middleware executes the following logic in strict order: (1) Instantiate a Supabase server client using createMiddlewareClient from @supabase/auth-helpers-nextjs, passing { req, res } to enable cookie mutation for token refresh. (2) Call await supabase.auth.getSession(). (3) If session is null or getSession() throws any error: immediately return NextResponse.redirect(new URL('/login', req.url)) — no fallback, no default role assignment, no page render (Iron Law 4). (4) If session exists but the JWT is expired, the Supabase client automatically attempts refresh using the refresh_token cookie. If refresh fails or refresh_token is absent: immediately return NextResponse.redirect(new URL('/login', req.url)). (5) If session is valid: query the users table using the service-role Supabase client (to bypass RLS for this internal lookup) for the row matching id = session.user.id. (6) If the query returns an error, returns zero rows, or the returned user's organization_id is null: immediately return NextResponse.redirect(new URL('/login', req.url)) — never render a default or wrong-role page (Iron Law 4 strict enforcement). (7) If the user row is found and valid: clone the request headers and set: x-user-id = user.id, x-organization-id = user.organization_id, x-user-role = user.role (one of: admin, member, viewer). (8) Return NextResponse.next({ request: { headers: clonedHeaders }, response: res }) to proceed. API route handlers read x-user-id, x-organization-id, and x-user-role from request.headers to enforce role-based logic. All Supabase DB queries in API routes additionally rely on organization_id-scoped RLS policies as a second enforcement layer. The middleware never caches role data in cookies or local state; every request re-validates from the database to prevent stale role exploitation.

#### Permissions model
Benavora uses a flat three-tier RBAC model (admin > member > viewer) enforced at two independent layers: (1) Middleware header injection and API route role checks, and (2) Supabase Row-Level Security policies. Every table that contains organization data carries an organization_id column. RLS is enabled on all such tables. The canonical RLS policy pattern for SELECT is: USING (organization_id = (SELECT organization_id FROM users WHERE id = auth.uid())). For INSERT: WITH CHECK (organization_id = (SELECT organization_id FROM users WHERE id = auth.uid())). For UPDATE and DELETE: USING (organization_id = (SELECT organization_id FROM users WHERE id = auth.uid())). Role-specific write restrictions (e.g., viewer cannot INSERT) are enforced at the API route layer by checking x-user-role from middleware headers before executing any DB mutation. The users table itself has an RLS policy allowing users to SELECT only their own row (id = auth.uid()) for non-admin reads, and allowing admins to SELECT all rows within their organization (organization_id match). Admin-only operations — team invitations, user role updates, user removal, organization settings updates, agent configuration management — return HTTP 403 immediately if x-user-role is not 'admin'. Viewer-only restrictions — blocking all mutations (POST, PATCH, PUT, DELETE) except marking their own alerts read — are enforced by checking x-user-role = 'viewer' in each mutating API route and returning HTTP 403 with { error: 'Viewers have read-only access.' }. Cross-organization data isolation is guaranteed by the combination of organization_id RLS policies and the middleware-injected x-organization-id header being used as the authoritative scope value in all API queries — the API never trusts a client-supplied organization_id in the request body for scoping purposes.
