## Agent Orchestration Flow

### Primary Flow: Research Run Orchestration

1. **Trigger:** User clicks 'Run Research' → `POST /api/research/run`
2. **Pre-flight check:** API checks for existing `research_runs` row with `status='running'` for the `organization_id`; returns HTTP 409 if found.
3. **Setup:** INSERT `research_runs` row (`status='running'`, `started_at=now()`). INSERT one `research_run_agents` row per active agent config (`status='pending'`).
4. **Parallel Execution:** All ResearchAgent instances launched simultaneously via `Promise.allSettled`. Each agent updates its `research_run_agents` row to `status='running'` on start, then `status='completed'|'failed'` on finish. Supabase Realtime pushes these status changes to the frontend in real-time.
5. **Deduplication:** After `Promise.allSettled` resolves, the orchestrator aggregates all results and runs the deduplication pipeline (URL normalization → URL grouping → fuzzy name matching → metadata merging). Stats written to `research_runs.deduplication_stats`.
6. **Persistence:** Unique grants INSERTed into `grants` table with `source_type` from ResearchAgent classification.
7. **Eligibility Scoring (async, non-blocking):** For each newly inserted grant, EligibilityScoringAgent is dispatched asynchronously. If no search profile exists, grant is marked `eligibility_flag='unscored'`. Scoring does NOT block the research run completion response.
8. **Run Completion:** `research_runs.status` updated to `completed` or `partial`. Frontend receives completion signal.
9. **Alert Generation:** AlertGenerationAgent triggered with run summary. For each grant where EligibilityScoringAgent returns `high_match` and grant age <24h, AlertGenerationAgent also fires a `high_match_grant` alert.
10. **Consensus Validation (on-demand or auto for low-confidence grants):** Grants with `confidence_score < 0.7` from ResearchAgent automatically enqueue ConsensusValidationAgent. Users can also trigger manually via Grant Detail page → `POST /api/consensus/validate`.

### Secondary Flow: Manual Rescore
1. User clicks 'Re-score' on Grant Detail page → `POST /api/grants/[id]/rescore`
2. EligibilityScoringAgent runs synchronously (within API response timeout of 30s).
3. `grants` row updated; response returned to frontend.

### Secondary Flow: Consensus Validation
1. Triggered automatically for low-confidence grants after research run, or manually via UI.
2. ConsensusValidationAgent (GPT-4o) runs independently of primary assessment.
3. Orchestrator computes `consensus_score = (primary_confidence + secondary_confidence) / 2` and sets `source_type_agreement = primary_source_type === secondary_source_type` and `discrepancy_flag = |primary_eligibility_score - secondary_eligibility_score| > 20`.
4. Results written to `consensus_validations` table. `grants.consensus_validated=true` flag set.

### Timeout and Error Handling
- Each ResearchAgent promise has a 90-second hard timeout; on timeout, agent marked `failed` with `error='timeout'`.
- AI provider 429 responses trigger one retry after 5 seconds; second 429 marks agent `failed` with `error='rate_limited'`.
- A Vercel cron job (every 10 minutes) scans for `research_runs` with `status='running'` and `started_at < now() - interval '10 minutes'`; marks them `failed`.
- EligibilityScoringAgent failures do not block grant persistence; grant remains `eligibility_flag='unscored'`.
- AlertGenerationAgent failures are logged but do not affect core research flow; alerts can be regenerated on next run.

```

### Agent: EligibilityScoringAgent
- **Purpose:** Score a single grant's eligibility match for a specific organization using the organization's search profile and the grant's full details. Returns a 0-100 match score, a flag category, and a brief rationale.
- **Trigger:** Called asynchronously after each grant INSERT following deduplication in a research run, and on-demand via POST /api/grants/[id]/rescore. Invoked as a Supabase Edge Function or Next.js API background task.
- **Input contract:** { grant_id: string, organization_id: string, grant: { title: string, funder_name: string, program_name: string, description: string, source_type: string, amount_min: number|null, amount_max: number|null, deadline: string|null, tags: string[] }, eligibility_filters: { is_501c3: boolean, years_in_operation_min: number|null, annual_budget_min: number|null, annual_budget_max: number|null, staff_size_min: number|null, staff_size_max: number|null, served_population_tags: string[] }, focus_area_weights: Record<string,number>, amount_min: number|null, amount_max: number|null, geographic_scope: object }
- **Output contract:** { grant_id: string, score: number, eligibility_flag: 'high_match'|'moderate_match'|'low_match'|'unscored', rationale: string, scored_at: string }
- **Model:** `claude-opus-4-5`
- **Token budget:** 1024

**System prompt:**
```
You are a nonprofit eligibility assessment specialist. Your task is to score how well a specific grant opportunity matches an organization's profile and needs. Analyze the grant details against the organization's eligibility filters, focus area weights, budget requirements, geographic scope, and funding preferences. Return a JSON object with exactly these fields: score (integer 0-100, where 100 is a perfect match), rationale (string of 2-3 sentences explaining the score, citing specific matching or mismatching criteria). Scoring guidelines: 80-100 indicates strong alignment across eligibility requirements, focus areas, geography, and funding amounts; 50-79 indicates partial alignment with some gaps; 0-49 indicates significant misalignment or likely ineligibility. Be specific in your rationale — mention the grant name, key matching factors, and any disqualifying criteria. If eligibility_filters indicate the organization lacks a required characteristic (e.g., grant requires 501c3 and org may not qualify), score accordingly.
