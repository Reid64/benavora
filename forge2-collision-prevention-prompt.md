# FORGE 2.0 Build Task: Shared-Path Collision Prevention for Concurrent Queue Execution

## Problem statement (real, observed incident — not hypothetical)

During a Tarritrix build session on 2026-08-15, `docs/decisions/escalate-signal-options.md` was independently regenerated by at least three separate Claude Code sessions (a FORGE-orchestrated queue run and multiple direct interactive sessions), each unaware the others existed or had already produced output at the same path. This caused three separate git merge conflicts in one evening, each requiring manual operator review of two AI-generated drafts to determine which was more complete/correct before resolving. No data was lost, but real operator time was spent adjudicating conflicts that should never have been possible to create in the first place.

Root cause: any prompt whose output target is a **shared/canonical path** (a governance doc like `STATE_OF_THE_BUILD.md`/`SCHEMA_REGISTRY.md`, a decision doc, an audit doc — anything not uniquely namespaced per-agent/per-feature) is a collision risk the moment more than one session can run concurrently against the same repo. Per-agent code files (e.g. `src/lib/agents/a-43-trust-signal-composer.ts`) never had this problem tonight, because each agent's output path was already unique by construction — the failure mode is specific to shared cross-cutting files, not general.

## Required capability

Implement a **scratch-then-promote** write pattern as a first-class feature of FORGE 2.0's queue execution engine, so this failure mode becomes structurally impossible rather than something an operator has to catch and resolve after the fact.

### 1. Path classification

Add a `path_class` field to each prompt's `expected_outputs`/`gates.file_exists.files` declarations in the queue schema:

```yaml
gates:
  - type: file_exists
    files:
      - path: docs/decisions/escalate-signal-options.md
        path_class: shared_canonical
      - path: src/lib/agents/a-43-trust-signal-composer.ts
        path_class: unique_per_task
```

- `unique_per_task` (default if unspecified, for backward compatibility): no special handling, current behavior.
- `shared_canonical`: any path also declared as a governance doc in the queue's `governance:` list, or any path matching an operator-configurable glob list (default seed: `docs/decisions/**`, `docs/audits/**`, `STATE_OF_THE_BUILD.md`, `SCHEMA_REGISTRY.md`, `BEHAVIORAL_CONTRACTS.md`, `AGENTS.md`, `BLUEPRINT.md`).

### 2. Scratch-write enforcement for `shared_canonical` paths

When a prompt's declared output includes a `shared_canonical` path, the Build Agent invocation must be automatically rewritten (prepended instruction, not left to the prompt author to remember) so the agent writes to a scratch path instead of the real one:

```
docs/_forge-scratch/{queue_id}/{prompt_id}/{run_timestamp}/{original_filename}
```

Example: `docs/_forge-scratch/tarritrix-cleanup-repairs/escalate-decision-001/20260815-143022/escalate-signal-options.md`

The `file_exists` gate for that prompt checks the scratch path, not the canonical one — the prompt's own success/failure is unaffected by this change, it just never touches the shared file directly.

### 3. Promotion as a separate, explicit, single-owner step

Add a new gate type, `promote_scratch`, usable as the final gate on a queue or as its own dedicated queue entry:

```yaml
gates:
  - type: promote_scratch
    scratch_glob: "docs/_forge-scratch/{queue_id}/**/*.md"
    canonical_mapping:
      "escalate-signal-options.md": "docs/decisions/escalate-signal-options.md"
```

Behavior:
- Run `git pull` immediately before comparing/writing to the canonical path (minimizes the collision window to the promotion step's own short runtime, not the full duration of every session that might write to it).
- If the canonical path doesn't exist yet, or exists but is byte-identical to the scratch content, copy directly — no conflict possible.
- If the canonical path exists and differs, **do not auto-merge**. Write both versions to a real, timestamped `docs/_forge-scratch/_pending-review/` location and halt the queue with a clear operator-facing message identifying both file paths for manual review — this is a deliberate escalation to a human decision, not a silent pick.
- On successful promotion: `git add` the canonical path only (never `git add -A` — this project's existing standing rule against sweeping in unrelated dirty files, e.g. `.claude/worktrees/*` submodule pointers, applies here too), commit with a message identifying the source queue/prompt/scratch-timestamp for full traceability, and `git push` immediately — the smallest possible window between write and push, not batched with unrelated work.
- Clean up: delete the promoted scratch file (or the whole `docs/_forge-scratch/{queue_id}/` tree once all its outputs are promoted) so scratch space doesn't accumulate indefinitely.

### 4. Concurrent-session awareness (defense in depth, not the primary mechanism)

Before any `shared_canonical`-path prompt begins execution, check for a lock file:

```
docs/_forge-scratch/.locks/{canonical_path_hash}.lock
```

containing `{queue_id, prompt_id, pid, acquired_at}`. If a lock exists and is younger than a configurable staleness threshold (default 30 minutes), the prompt should wait/retry rather than proceed — two sessions racing to produce the same canonical doc should serialize, not both burn 10+ minutes of real build time producing redundant drafts. Release the lock when the scratch write completes (not when promotion completes — promotion is a separate, later step and shouldn't hold the lock that long).

### 5. Backward compatibility

Every existing queue file in this project's library (the 34-entry manifest at `C:\Users\manag\Documents\FORGE\library\Tarritrix\library-manifest.yaml`) uses `unique_per_task` paths implicitly today except for governance-doc updates baked into nearly every prompt's final steps (e.g. "Update STATE_OF_THE_BUILD.md..."). Those governance-doc-update instructions are the most common real source of this collision risk and should be the first real-world validation case — retrofit the `shared_canonical` classification onto `STATE_OF_THE_BUILD.md` and `SCHEMA_REGISTRY.md` specifically and confirm two prompts from different queues can both update governance docs in the same overnight run without conflict, before rolling this out further.

## Acceptance criteria

- A test scenario reproducing tonight's real incident (two concurrent Build Agent invocations both instructed to write `docs/decisions/some-topic.md`) completes with zero git conflicts and a clear, human-readable log of what was scratch-written, what was promoted, and what (if anything) required manual review.
- `git log` for any `shared_canonical` path shows one commit per genuine promotion, never a merge-conflict-resolution commit.
- The lock mechanism does not deadlock — a crashed session's stale lock is automatically reclaimable after the staleness threshold.
- Full inline TypeScript implementation for the scratch-write path rewriting, the `promote_scratch` gate, and the lock mechanism — no pseudocode, no TODOs, matching this project's own standing engineering-density requirement.
